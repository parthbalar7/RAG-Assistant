# RAGv2 Integration Roadmap

Synthesized from 6 area-mapping agents (retrieval models, chunking/ingestion, graph, memory, pipeline orchestration, efficiency). 28 raw recommendations deduped into this roadmap, then adversarially fact-checked on 2026-07-08: every model ID, license, API shape, and arXiv reference below was verified against the live source (corrections and three verified additions — items 1.0, 1.14, and the static-embeddings note in 1.12 — are folded in). Constraints honored throughout: local-first, CPU-only (24GB RAM), ChromaDB stays, Apache/MIT dependencies only.

**Cross-cutting note — the rerank_score bug:** three agents independently flagged that `rerank()` in `core/retriever.py` stores raw CrossEncoder logits, while `core/gap_analyzer.py:89` compares `rerank_score` against `GAP_SCORE_THRESHOLD=0.45` as if it were a probability. Apply `sigmoid()` in `rerank()` once (item 1.3) and every downstream consumer (gap analyzer, generator display, agent, any future reranker backend) is fixed together.

## Tier 1 — Quick wins (hours to 1 day)

### 1.0 Raise Ollama's context window (do this before anything else)
On CPU/low-VRAM boxes Ollama defaults to a **4k-token context window** and **silently truncates** anything beyond `num_ctx` — no error, the model just never sees the dropped tokens. This project's prompt is exactly the kind that blows past 4k: system prompt + 6 history turns + memory block + `top_k` retrieved chunks. Every retrieval-quality improvement below is invalidated if the chunks it retrieves get truncated before generation. Fix: set `OLLAMA_CONTEXT_LENGTH` (or pass `options={"num_ctx": settings.ollama_num_ctx}` in `_ollama_chat`, new config field, e.g. 16384 for qwen2.5-coder:14b — KV RAM cost is manageable with `q8_0` KV quantization from 1.2). Also add a defensive token count in `core/generator.py:_build_messages` that logs a warning when the assembled prompt exceeds the configured window.
**Deps:** none. **Sources:** https://docs.ollama.com/faq

### 1.1 Fix the chunk-size / MiniLM-window mismatch
`config.py` sets `chunk_size=512` (tiktoken cl100k via `count_tokens` in `core/ingestion.py`), but all-MiniLM-L6-v2's `max_seq_length` is 256 wordpiece tokens — **every full-size chunk is silently truncated roughly in half** before reaching ChromaDB, and the ms-marco cross-encoder truncates query+chunk pairs at 512 too. Change defaults to `chunk_size≈220-256`, `chunk_overlap≈0-32` (Chroma's chunking report found ~200 tokens/no-overlap best); zero code changes since `_chunk_code` and `_chunk_prose` both read settings. Must land **first** — breadcrumbs (1.7) and contextual retrieval (2.4) prepend text that must also fit the window. Caveat: re-chunking shifts `_generate_chunk_id(path,start,end)` boundaries and `upsert` doesn't delete old-boundary chunks — users must `clear()`/`delete_file()` before re-ingesting (worth adding auto-delete-by-path in `add_chunks`).
**Deps:** none. **Sources:** https://www.trychroma.com/research/evaluating-chunking

### 1.2 Ollama keep_alive + KV-cache quantization
The single biggest perceived-latency item on the local backend: qwen2.5-coder:14b is evicted after Ollama's default 5-minute idle, so every post-pause query pays a full cold load. Add `keep_alive=settings.ollama_keep_alive` (new config field, default `"1h"`) to both `client.chat()` calls in `_ollama_chat` (`core/llm_client.py` ~lines 253, 288), and thread an optional `keep_alive` kwarg so `get_memory_model()` callers (llama3.2:3b extraction) can pass `"1m"` to avoid evicting the resident 14b — or document `OLLAMA_MAX_LOADED_MODELS=2`. Host-side, set `OLLAMA_KV_CACHE_TYPE=q8_0` (halves KV RAM; fact-check note: flash attention is now enabled automatically when the backend supports it, so `OLLAMA_FLASH_ATTENTION=1` is harmless but no longer required; and `OLLAMA_MAX_LOADED_MODELS` already defaults to 3 on CPU, so the 14b+3b pair can co-reside out of the box if RAM allows). `_build_messages` in `core/generator.py` is already prefix-stable for Ollama's automatic KV reuse — just don't break that invariant.
**Deps:** none (env vars + one kwarg). **Sources:** https://smcleod.net/2024/12/bringing-k/v-context-quantisation-to-ollama/

### 1.3 Pre-generation retrieval-confidence gate (CRAG-style) + the sigmoid fix
Step 1 is the bug fix above: store `hit['rerank_score'] = sigmoid(logit)` in `rerank()` so scores are in (0,1), then recalibrate `GAP_SCORE_THRESHOLD` (~0.5-0.6). Step 2: split `analyze()` in `core/gap_analyzer.py` into `analyze_pre(query, hits)` (Signals 1-3, pure heuristics, <1ms) and the existing post-generation Signal 4. Step 3: in `_handle_rag_query` (`api/routers/websocket.py`), call `analyze_pre` after hits are computed but **before** the `generate_stream` producer thread starts — on gap, emit `gap_detected` with `stage:'pre'` so the frontend `GapPrompt` offers DDG augmentation before a bad answer streams. Optional one-shot query-rewrite retry behind `RAG_PRE_GEN_REWRITE` (default false on Ollama). Happy-path cost is ~0ms.
**Deps:** none. **Sources:** https://arxiv.org/abs/2401.15884

### 1.4 Replace the BFS graph walk with Personalized PageRank (HippoRAG 2, natively)
In `graph_retrieve()` (`core/knowledge_graph.py:281-420`), keep the cosine seed selection over `_entity_vecs` but replace the BFS block (lines 323-358) with `nx.pagerank(graph.to_undirected(), alpha=0.85, personalization={k: max(sim,0) ...}, weight='weight')` — edge weights already increment on repeated relations, so PPR is weight-aware for free. Score chunks by summing PPR mass over referencing nodes, normalized to [0,1], replacing the hardcoded `score=0.7` at line 414 and the flat 50-chunk dump at line 395. For HippoRAG 2's passage integration, pass the vector-hit chunk ids from `_handle_rag_query` and boost personalization for entities intersecting them. Fall back to BFS on `PowerIterationFailedConvergence`; regenerate the `graph_path` WS payload from PPR results so the frontend viz stays meaningful. ~40-60 line diff.
**Deps:** none — networkx (already present) ships personalized pagerank. **Sources:** https://arxiv.org/abs/2502.14802

### 1.5 Composite memory ranking: relevance × recency × importance
Half-built already: `EXTRACT_SYSTEM` requests an importance score and `add_fragment` stores it, but `retrieve_memories` (`core/memory.py:512`) ranks by pure cosine — importance is stored and never used. Over-fetch top-20, rescore as `0.4*similarity + 0.3*exp(-decay*hours_since(last_accessed)) + 0.3*importance`, inject top `memory_top_k` as now. Add `last_accessed`/`access_count` metadata with a batched `collection.update` touch on injection (reinforcement); `search()` must start returning `fragment_id` (currently omitted). Backward compat is free via `meta.get("last_accessed", meta.get("created_at", 0))`.
**Deps:** none. **Sources:** https://memx.app/glossary/generative-agents/

### 1.6 Multi-query expansion fused into existing RRF (RAG-Fusion)
New `core/multi_query.py` mirroring `core/hyde.py`: one `llm_client.chat()` call generates 2-3 paraphrases + one step-back generalization (reuse `decompose()`'s memory-model-with-fallback and `_parse_sub_queries`; return `None` on failure). In `retrieve()`, run vector+sparse per variant, generalize `_rrf_merge` to accept N ranked lists (it's already a rank-sum loop), then rerank against the **original** query. Wire `use_multiquery` through the WS payload like `use_hyde`, add a Settings → Retrieval toggle in `src/App.js`, and treat HyDE/multi-query as either/or in the UI. Benchmarks say this beats HyDE on real documents, and the weak 384-dim MiniLM embedder is exactly the vocabulary-mismatch case it fixes.
**Deps:** none; one extra LLM call per cache-miss query (absorbed by `core/query_cache.py` on repeats). **Sources:** https://dl.acm.org/doi/10.1145/3728199.3728221

### 1.7 Deterministic heading-path / file-symbol breadcrumbs on chunks
`_chunk_prose` detects headings then throws them away. Maintain a heading stack, set `metadata['heading_path']`, and prepend a one-line breadcrumb (`[docs/guide.md > Installation > Docker]`) to `chunk.content` before `add_chunks`; for code, prepend `# path/file.py:AA-BB (python)`. Because BM25 and SPLADE both rebuild from collection documents, the breadcrumb reaches dense **and** both sparse retrievers with zero extra plumbing. Also fix the PDF hole: `core/multimodal.py` emits `--- Page N ---` markers that `_chunk_prose` ignores (whole PDFs become one windowed mega-section) — treat page markers as boundaries, or better, chunk at PageIndex tree-node page ranges when a tree exists. **Required companion fix:** `_rrf_merge` dedups on `hit['content'][:100]`, which shared breadcrumbs would poison — key on `metadata['source']` instead. Keep breadcrumbs under ~25 tokens (pairs with 1.1).
**Deps:** none; requires clear + re-ingest. **Sources:** https://docling-project.github.io/docling/concepts/chunking/

### 1.8 Semantic query-cache eligibility, TTL, and gap-aware store ordering
Three correctness holes in an otherwise well-tuned cache: (1) cache hits bypass conversation history and memory entirely, so anaphoric follow-ups ("what does it return?") can be served answers minted in another conversation — add `is_cache_eligible()` skipping <3-content-word and pronoun-pivot queries, plus `is_multi_part()` queries at store time; (2) in `_handle_rag_query` the cache store (~line 467) runs **before** `analyze_gap` (~line 495), so "I don't have information on…" answers get cached and replayed — reorder and skip storing on `gap.is_gap`; (3) `QueryCache.lookup()` never checks the stored `ts` — add a TTL (default 24h). Bonus: a negation/qualifier token guard (not/without/except/latest) after the cosine test, since MiniLM scores opposite-qualifier paraphrases above 0.93.
**Deps:** none. **Sources:** https://www.infoq.com/articles/reducing-false-positives-retrieval-augmented-generation/

### 1.9 Gap Signal 5: groundedness from the already-computed provenance map
`compute_provenance` already runs in `_handle_rag_query` (lines 479-491) immediately before `analyze_gap` and produces `novel_fraction`/`doc_coverage` from local embeddings — a free groundedness signal gap analysis ignores. Pass the `ProvenanceMap` into `analyze()`: if `novel_fraction > ~0.5` and `doc_coverage < ~0.3`, declare a gap ("answer mostly unsupported by retrieved chunks") — catches confident hallucinations that never say "I don't have information", unlike Signal 4's regex. Same one-liner in `_handle_pageindex_query`. Optional tier 2 behind `RAG_ANSWER_CRITIC`: one post-stream llama3.2:3b yes/no supportedness call whose "missing" field sharpens the DDG search topic. Skip Signal 5 for code-heavy answers (provenance sentence-splitting handles code poorly).
**Deps:** none for tier 1. **Sources:** https://www.meilisearch.com/blog/self-rag

### 1.10 Time-aware memory: dates in the injected block + temporal filtering
`retrieve_memories` formats fragments as `- {content} ({sim}%)` — the LLM never sees when a fact was learned, so "what did I decide last month" fails structurally. Format as `- {content} [{YYYY-MM-DD}] ({sim}%)` from `created_at` (zero cost), and add a regex pass for temporal phrases ("yesterday", "last week", "in June") that computes a date range passed to `MemoryStore.search` as a Chroma `{"created_at": {"$gte": lo, "$lte": hi}}` filter — extends the existing `where_filter` at `core/memory.py:194`. A regex miss just means no filter, i.e. today's behavior.
**Deps:** none. **Sources:** https://arxiv.org/abs/2410.10813

### 1.11 Anthropic prompt caching (cache_control) — biggest for the agent loop
In `_anthropic_chat` (`core/llm_client.py` ~line 147), send `system` as a structured block with `cache_control: {"type": "ephemeral"}` and add a breakpoint on the last message preceding the newest turn. The real payoff is `run_agent()` in `core/agent.py`: up to `agent_max_steps=5` calls per query with a byte-identical growing prefix full of search-result dumps — each iteration re-reads prior context at 0.1x price. Extend the usage dict with `cache_creation_input_tokens`/`cache_read_input_tokens` so cache hits are verifiable. Zero effect on the Ollama path.
**Deps:** none (anthropic SDK supports it); only reduces the optional paid-API bill. **Sources:** https://platform.claude.com/docs/en/build-with-claude/prompt-caching

### 1.12 ONNX backend for the embedder (and optionally the cross-encoder)
`get_embedding_model()` becomes `SentenceTransformer(model, backend=settings.embedding_backend)` with try/except fallback to torch (same pattern as the SPLADE degrade). 2-3x CPU speedup on every path reaching `embed_texts()` — cache-miss queries, bulk ingest, HyDE, memory. Existing caches survive (SHA-256 text keys are backend-agnostic; ~1e-6 cosine drift is harmless). **Sequencing note:** if the gte-modernbert swap (2.1) is planned, do this after — verify ONNX weights exist for whichever model wins. **Fact-check addition:** for hot side-paths where quality matters less than latency — provenance sentence scoring (1.9), the N×N alias-edge matmul (2.3), query-cache embeds — consider a static embedding model (`sentence-transformers/static-retrieval-mrl-en-v1` or Model2Vec "potion" models, Apache 2.0): ~100x faster than MiniLM on CPU at ~85-90% retrieval quality. Not a primary-embedder replacement, but a much bigger lever than ONNX for those specific paths.
**Deps:** `pip install sentence-transformers[onnx]` (~50MB onnxruntime wheel); static models are plain sentence-transformers. **Sources:** https://sbert.net/docs/sentence_transformer/usage/efficiency.html, https://huggingface.co/blog/static-embeddings

### 1.13 BM25S swap for rank_bm25 (opportunistic, low priority)
Confined to `BM25Index` in `core/retriever.py`; keep the load-bearing `doc_ids/doc_contents/doc_metadatas` attributes (read by `_refresh_metadata_cache`). Day-to-day gains are barely perceptible at single-user scale — the value is removing the scaling cliff where `_rebuild_indexes()` re-tokenizes the entire collection on every `add_chunks()` (each web-augment) and server start, plus optional `mmap=True` persisted indexes. Watch the tokenizer change: bm25s stems and strips stopwords, which may hurt code identifiers — pass a custom splitter.
**Deps:** `pip install bm25s[full]` (MIT, ~51MB). **Sources:** https://github.com/xhluca/bm25s

### 1.14 Schema-constrained JSON via Ollama structured outputs
Every LLM-emits-JSON path in the codebase — memory extraction (`EXTRACT_SYSTEM`), query decomposition (`_parse_sub_queries`), the agent's tool calls (`_parse_tool_call`), and the planned Mem0 ops (2.2) / learned router (2.10) — currently relies on prompt-and-pray parsing with fail-open fallbacks, which on 3B models means frequent silent no-ops. Ollama has supported schema-constrained decoding since late 2024: pass a JSON schema as the `format` parameter to `client.chat()` and the output is near-guaranteed to parse. Add an optional `json_schema` kwarg to `llm_client.chat()`/`chat_with_usage()` that maps to `format` on the Ollama path (and to a tool-use or prefilled-JSON pattern on Anthropic, or simply ignore there — Claude parses fine unconstrained). Zero dependencies, converts the weakest links of the local pipeline into reliable ones.
**Deps:** none (ollama-python already supports `format`). **Sources:** https://ollama.com/blog/structured-outputs

## Tier 2 — Medium (1-3 days)

### 2.1 Embedder modernization: gte-modernbert-base with cache versioning + migration *(merged: 2 recs)*
Swap `RAG_EMBEDDING_MODEL` to `Alibaba-NLP/gte-modernbert-base` (768-dim, 8192-token context, Apache 2.0, strong on code, no query/doc prefixes needed). The swap is config-only because `embed_texts()` is the single chokepoint for docs, memory, KG vectors, and query-cache embeds — but three code changes are mandatory: (1) per-model embed-cache paths in `core/embed_cache.py` (`embed_cache_{sha256(model)[:8]}.npz`) or stale 384-dim vectors crash Chroma; (2) a dimension guard in `VectorStore.__init__`/`MemoryStore` comparing a stored embedding against the model dimension, failing with a pointer to (3) `scripts/migrate_embeddings.py`, which re-embeds all collections (`docs_{uid}`, `memories_*`, legacy `tech_docs`) in batches. Also replace the hardcoded MiniLM in `core/provenance.py:46` with `get_embedding_model()` so two models aren't resident in RAM. Hidden win: the 8192-token window permanently fixes the truncation class of bug from 1.1. **Optional follow-on** (only after this lands, and only if benchmarked worthwhile): `Qwen/Qwen3-Embedding-0.6B` as a documented "high quality" `RAG_EMBEDDING_MODEL` value — needs an `is_query` role flag through `embed_texts()` plus role-sentinel cache keys, and costs 5-15x MiniLM per chunk on CPU.
**Deps:** none new; pin `transformers>=4.48`; model ~600MB fp32 (Qwen3: ~1.2GB). **Sources:** https://huggingface.co/Alibaba-NLP/gte-modernbert-base, https://qwenlm.github.io/blog/qwen3-embedding/

### 2.2 Mem0-style write reconciliation with soft invalidation *(merged: 2 recs)*
Two agents converged on the same fix from Mem0 and Graphiti/Zep angles: `add_fragment` (`core/memory.py:147`) only skips near-exact duplicates (cosine>0.92), so contradicting facts ("switched from CRA to Vite") accumulate forever and both get injected. Port the Mem0 update phase natively (~50 lines, **not** the mem0ai library): when the top match falls in the 0.55-0.92 band, one `get_memory_model()` call returns `{"op": "ADD|UPDATE|DELETE|NOOP", ...}`; DELETE is Graphiti-style **soft** invalidation (`invalid_at=time.time()`, `superseded_by=<id>` via `collection.update` — never hard-delete, so mistakes are reversible and inspectable in the memory browser). `search()` over-fetches and post-filters invalidated fragments (backward-compatible with fragments lacking the key). Fail-open to plain ADD on any LLM/JSON error — strictly no worse than today. Latency is invisible: writes already run in a daemon thread via `process_memories_background`.
**Deps:** none; one extra llama3.2:3b call per candidate-contradiction write. **Sources:** https://arxiv.org/abs/2504.19413, https://github.com/getzep/graphiti

### 2.3 LLM-free graph construction: spaCy NER + code-identifier regex + alias edges
`build_from_store()` (`core/knowledge_graph.py:160-277`) sends every chunk through the LLM in batches of 3 — hours on CPU for 1000 chunks — **and has an attribution bug**: each extracted entity is attached to ALL chunk_ids in its batch (the zip loop at lines 228-230), smearing provenance. Add `RAG_GRAPH_EXTRACTION` (`ner|llm|hybrid`, default `ner`): per-chunk spaCy `en_core_web_sm` for prose, CamelCase/snake_case regex for code (chunk metadata already carries `language`), correct single-chunk attribution, `co_occurs` edges reusing the existing weight-increment dedup. Then one N×N cosine matmul over the already-built `_entity_vecs` cache adds `alias_of` edges above ~0.85 — fixing `_canon()`'s lower-strip-only weakness and giving PPR (1.4) synonym bridges. `hybrid` mode keeps LLM extraction for the top ~50 high-degree entities only.
**Deps:** `spacy>=3.7` + `en_core_web_sm` (~50MB; add `python -m spacy download` to Dockerfile). **Sources:** https://arxiv.org/abs/2505.24226

### 2.4 Opt-in contextual retrieval at ingest (Anthropic-style, via Ollama or Haiku)
New `core/contextualizer.py` mirroring `core/hyde.py`: `situate(doc_text, chunk_text)` makes one small-model call per chunk (llama3.2:3b locally, Haiku with prompt caching when the Anthropic key is set), returns `''` on any exception. Hook in `api/routers/ingest.py` between `ingest_directory()` and `add_chunks()`; storing enriched text as the Chroma document gives contextual embeddings + contextual BM25 + contextual SPLADE automatically (both sparse indexes rebuild from collection documents). The SHA-256 embed cache needs zero changes. Must stay opt-in (`contextual_enrich=False`): 2-6s/chunk on CPU Ollama means hours for 1000 chunks — prefer fast un-enriched ingest with background enrichment + re-upsert. For small corpora, the free breadcrumbs (1.7) may capture most of the benefit — measure with 2.5 before committing.
**Deps:** none new (llama3.2:3b already the memory model; Haiku ~$1/M doc tokens optional). **Sources:** https://www.anthropic.com/news/contextual-retrieval

### 2.5 Offline eval harness: deterministic retrieval metrics first, DeepEval second
The project has zero eval (`core/evaluation.py` was deleted) while exposing 9 unmeasured retrieval toggles. Step 1: `save_messages()` already accepts `metadata` and SQLite has the column — log `{config: toggles+model, contexts: [h["content"][:800]]}` per turn from `_handle_rag_query` to build an eval corpus from real usage for free. Step 2: `tests/eval/golden.jsonl` (20-50 questions → expected `document_path`). Step 3: `scripts/eval_retrieval.py` calls `core.retriever.retrieve()` directly per toggle combination, computes hit-rate@5/MRR — seconds, deterministic, no judge, and directly answers "does SPLADE/HyDE/reranking help on MY corpus". Step 4: DeepEval Faithfulness/ContextualRelevancy with a custom `DeepEvalBaseLLM` wrapping `llm_client.chat()` on Ollama — comparative scores only (±0.1 judge noise), never a CI gate. **This should land before or alongside 2.1/2.4/2.6 so their gains are measurable.**
**Deps:** `pip install deepeval` (Apache 2.0); existing Ollama models as judge. **Sources:** https://deepeval.com/blog/deepeval-vs-ragas, https://arxiv.org/abs/2511.04696

### 2.6 Configurable reranker: gte-reranker-modernbert-base and/or answerai-colbert-small-v1 *(merged: 2 recs)*
First the plumbing: `get_reranker()` hardcodes ms-marco at `core/retriever.py:36` — add `RAG_RERANKER_MODEL` + `reranker_type` (`cross-encoder|colbert`) to config with try/except fallback (SPLADE pattern), and normalize scores into (0,1) per 1.3 so `gap_analyzer` thresholds survive any backend. Two upgrade paths: (a) `Alibaba-NLP/gte-reranker-modernbert-base` (149M, 8192-ctx — no more pair truncation, drop-in CrossEncoder API, but ~5-10x latency ≈ 0.5-2s on 10-20 pairs); (b) `answerdotai/answerai-colbert-small-v1` (33M MaxSim via the `rerankers` package) — best quality-per-CPU-ms, BEIR 53.79 beats 109M cross-encoders at roughly today's ms-marco cost, but MaxSim scores are unbounded so per-batch normalization is not optional. Measure both with 2.5 and keep whichever earns its latency; per EncouRAGe, reranking sometimes doesn't.
**Deps:** (a) none, ~600MB model; (b) `pip install rerankers` (verify Windows/Docker), ~130MB model. Both Apache 2.0. **Sources:** https://huggingface.co/Alibaba-NLP/gte-reranker-modernbert-base, https://www.answer.ai/posts/2024-08-13-small-but-mighty-colbert.html

### 2.7 Idle-time memory maintenance job + procedural style-rules block *(merged: 2 recs)*
The hard part exists: `consolidate_memories()` (`core/memory.py:606`) does clustering + LLM merge but only runs on manual POST. Add a `lifespan` asyncio task (`api/server.py:34`) that every ~10 min runs `asyncio.to_thread(run_maintenance, uid)` for users idle >30 min with new writes: existing consolidation (using the stronger 14b model off the request path) + bounded pruning above `memory_max_fragments` (soft-archive lowest `importance × recency × usage` scorers) + automatic `process_session_summary`. In the same pass, distill all `pref` fragments into ≤5 bullet rules stored as one `proc_{user_id}` fragment, prepended under `[Style rules]` in `safe_retrieve_memories` (`api/helpers.py:40`) — fixes the structural bug where "answer concisely" only surfaces when cosine-similar to the query. Guard with a per-user lock shared with `add_fragments`; tolerate Ollama being unreachable.
**Deps:** none — plain asyncio, existing models. **Sources:** https://www.letta.com/blog/sleep-time-compute/, https://www.langchain.com/blog/langmem-sdk-launch

### 2.8 AST-aware code chunking via astchunk
`_chunk_code` splits on top-level regexes only — nested functions, methods after long bodies, and decorator-heavy code get merged or cut arbitrarily, hurting embeddings and the agent's `search`/`get_file` tools. For python/java/csharp/typescript, try astchunk's `ASTChunkBuilder` (size calibrated to the 1.1 target via `count_tokens`) mapped onto the existing `Chunk` dataclass — line spans are preserved so `_generate_chunk_id` and downstream metadata keep working; fall back to regex on ImportError/parse failure. Whole-function chunks are also the natural parent producer for 2.9.
**Deps:** `pip install astchunk` (MIT; tree-sitter grammars, Windows/Docker wheels OK). **Sources:** https://arxiv.org/abs/2506.15655

### 2.9 Small-to-big parent expansion after reranking
Once 1.1 shrinks chunks to ~220 tokens, add `_expand_to_parents(store, hits, budget_tokens=800)` **after** `rerank()` (rerank small, expand winners — the cross-encoder truncates at 512 anyway): fetch siblings by `document_path` metadata, stitch contiguous neighbors by `start_line` up to budget, stopping at `heading_path` changes (from 1.7). Better variant with 2.8: store AST-parent text in a `{collection}_parents` collection keyed by `parent_id`. Expose as WS flag `use_parent_expand` like `use_hyde`. Gotcha: in `websocket.py`, graph hits are appended after `retrieve()` returns — do the expansion in `_handle_rag_query` after the graph merge for parity. Dedup by parent/overlapping ranges so one function isn't sent twice.
**Deps:** none — pure metadata plumbing over ChromaDB. **Sources:** https://community.fullstackretrieval.com/indexing/parent-document-retriever

### 2.10 Trained 3-way complexity router replacing keyword heuristics
`route_query_fast()` (`core/router.py`) is substring matching that only tunes `top_k`, and "answer directly without retrieval" doesn't exist — the WS handler hard-errors on `s.count == 0`. Add `route_query_learned()`: TF-IDF + LinearSVC over `{direct, single, multi}` loaded from `data/router.joblib`, falling back to the heuristic when missing. `direct` → skip retrieval, stream with memory context only (also unblocks chatting before any docs are ingested); `multi` → force `decompose()` when `is_multi_part()`'s regex misses. Bootstrap from RAGRouter-Bench + ~50 hand-labeled queries from the existing SQLite `messages` table, and start logging (query, route, top rerank score) to analytics for retraining. Keep the agent REST-only.
**Deps:** scikit-learn (pin explicitly — already transitive), joblib. **Sources:** https://arxiv.org/abs/2403.14403

### 2.11 Wire up the dead `enrich_summaries` flag for PageIndex trees
`generate_tree_index()` accepts `enrich_summaries=True` but never uses it; `settings.pageindex_enrich_summaries` is a dead flag, and node summaries are just first-two-sentences boilerplate. Since `tree_search.py`'s `navigate_tree()` injects exactly these summaries into the navigation prompt, summary quality directly gates branch selection. Implement: after `_assign_node_ids`, per-node LLM summaries (cap ~40 nodes, largest first, per-node try/except keeping the local summary), run in a **background thread** after the tree JSON is cached, atomic-rewrite the cached `{doc_id}.json` (temp + `os.replace`), and stamp `summaries_enriched: true`. Matches the official VectifyAI PageIndex design.
**Deps:** none — `llm_client.chat()`, ~40 one-time calls per document. **Sources:** https://github.com/VectifyAI/PageIndex

### 2.12 Louvain communities with lazy LLM summaries ("themes in my docs")
At the end of `build_from_store()`, run `nx.community.louvain_communities(graph.to_undirected(), weight='weight', seed=42)` and stamp nodes with a `community` attribute (persists through the existing `nx.node_link_data` save). Expose via `get_viz_data()` (color-by-theme in the frontend force layout), `GET /api/graph/communities` (instant, pure graph math), and `POST /api/graph/communities/{cid}/summary` — generated **lazily** on first request from the community's top chunks, cached into the graph JSON. Zero indexing-time LLM cost, consistent with the repo's tree-search philosophy. Lands best **after** 2.3 densifies the graph with co-occurrence edges.
**Deps:** none — networkx 3.x includes louvain_communities. **Sources:** https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/

### 2.13 Bounded research loop: verify-after-augment with one refined follow-up
The `web_search_approved` handler (`websocket.py:79-99`) does exactly one `web_augment()` and never checks whether the gap closed. Wrap in a loop: re-run `retrieve()` + `analyze_pre()` (from 1.3); if still a gap and iteration < `RAG_RESEARCH_MAX_ITERS` (default 2), one LLM call produces a refined search query and augments again, emitting a `research_iteration` WS event. Finish by **auto-regenerating the answer** from the final hit set (factor the `generate_stream` producer block into a helper) instead of making the user re-ask — the biggest UX win. Tag round-2 chunks for bulk deletion via the existing `delete_file('web:...')` path and cap total ingested chunks per gap.
**Deps:** none (ddgs, web_augmenter in place); 1 LLM call per extra iteration, user opted in via GapPrompt. **Sources:** https://github.com/LearningCircuit/local-deep-research

## Tier 3 — Ambitious (1+ week, multi-part programs)

### 3.1 Retrieval-quality program: embedder + reranker + chunking, measured end-to-end
The full sequenced modernization: 1.1 (chunk sizes) → 2.5 baseline eval → 2.1 (gte-modernbert + migration) → 2.6 (reranker) → 2.8/2.9 (AST + parent expansion) → optional Qwen3-Embedding-0.6B profile, with a `make eval` gate between each step using the deterministic hit-rate@5/MRR harness on the golden set. Each piece is individually 1-3 days; run as a program it's a week-plus but is the only way to know which upgrades actually pay on this corpus rather than on BEIR. The Qwen3 step in particular should only survive if it beats gte on the user's real queries, since it costs 5-15x per-chunk CPU and a second full re-embed migration.
**Deps:** union of 2.1/2.5/2.6/2.8. **Sources:** as per constituent items.

### 3.2 Memory overhaul + LongMemEval regression harness
Combine 1.5, 1.10, 2.2, and 2.7 into a coherent memory rework, verified by a ~50-question LongMemEval-S subset in `tests/memory_eval.py` (standalone script, not pytest): replay haystack sessions through `process_turn_memories(user_id="eval", ...)`, answer via `retrieve_memories` + `llm_client.chat`, judge with the Anthropic key or slowly via Ollama, wire as `make memory-eval`. Run once before and once after — the temporal-reasoning and knowledge-update categories are exactly where today's ADD-only pure-cosine design should score worst, so the delta is the evidence. Cache the ingested eval store between judged runs; replaying 115K-token haystacks through 3B extraction on CPU takes hours otherwise.
**Deps:** LongMemEval dataset (~500MB, free); optional Anthropic key for judging. **Sources:** https://arxiv.org/abs/2410.10813, https://github.com/xiaowu0162/longmemeval

## Already state-of-the-art

- **Hybrid dense + sparse + RRF + cross-encoder rerank** (`core/retriever.py`) — the literature's standard 2025 recipe, with SPLADE learned sparse as a graceful-degrading option; the remaining gap is model vintage, not architecture.
- **Zero-LLM structural indexing + query-time LLM reasoning** (`core/tree_indexer.py` / `core/tree_search.py`) — exactly the LazyGraphRAG/E2GraphRAG prescription: never pre-summarize, spend LLM budget at query time.
- **Agent kept opt-in, off the WS hot path** (`core/agent.py`, REST `use_agent`) — matches 2026 controlled evidence that explicit rerankers beat LLM orchestration at 1/3 the tokens.
- **Fact-based memory extraction with LLM-assigned importance** (`extract_memories_from_turn`) — LongMemEval's "fact-augmented keys" fix is already the design; importance just needed retrieval-side use (1.5).
- **Content-hash embed cache + semantic query cache with event-driven invalidation** — 0.93 threshold sits in the tuned band; `invalidate_user_cache()` already fires on every corpus mutation.
- **HyDE default-off, per-query toggles, graceful degradation everywhere** (SPLADE→BM25, hyde→None) — validated by current benchmark configs.
- **User-approved web fallback** (gap_analyzer → GapPrompt → web_augmenter) — the human-in-the-loop pattern deep-research systems converge on.

## Considered and skipped

- **Full ColBERT/PLAID primary index (RAGatouille/PyLate)** — ChromaDB has no multi-vector support; the ColBERT *reranker* (2.6b) captures most of the benefit with zero storage changes.
- **Heavyweight 0.5B+ rerankers (bge-v2-m3, Qwen3-Reranker) & LLM-as-reranker** — multi-second CPU latency for single-digit nDCG on a no-GPU box.
- **Jina embeddings/rerankers** — CC-BY-NC license landmine; Apache equals-or-betters exist at every slot.
- **Binary/int8/Matryoshka quantization** — solves a millions-of-vectors problem this thousands-of-vectors app doesn't have; Chroma can't exploit it anyway.
- **Late chunking & semantic (breakpoint) chunking** — incompatible with the embedder/cache design and not evidence-supported vs the structure-aware boundaries already implemented.
- **Proposition/Dense-X indexing & full RAPTOR** — order-of-magnitude LLM rewrite cost, harmful for code; hierarchy already covered by PageIndex + KG.
- **Docling / Chonkie adoption** — hundreds of MB (or churn risk) for structure the repo already computes in `tree_indexer.py` and `_chunk_prose`.
- **HippoRAG 2 / fast-graphrag / LightRAG / nano-graphrag / full GraphRAG as dependencies** — GPU-class reference stacks, abandoned repos, or ≥32B-model extraction requirements; the portable ideas (PPR, co-occurrence build, lazy communities) are ported natively in 1.4/2.3/2.12.
- **Graphiti/Zep, MemOS, Letta, LangMem, mem0ai, A-Mem as frameworks** — each wants a second database or duplicates `core/llm_client.py`/`core/memory.py`; every transferable idea is ported dependency-free in 2.2/2.7/1.10.
- **Self-RAG checkpoints, CRAG's T5 evaluator, MiniCheck, Provence** — dedicated verifier/pruner models add downloads and CPU-seconds where existing rerank scores and `core/provenance.py` provide the same signals free (1.3/1.9).
- **Search-R1/DeepRetrieval RL agents & Speculative RAG** — require multi-GPU training/parallel-sampling infrastructure; only the logging idea survives, folded into 2.10.
- **EmbeddingGemma-308M** — dominated on this code-heavy corpus by gte-modernbert at half the compute, with a more restrictive license.
- **tantivy-py / DuckDB FTS / RAGAS** — heavier machinery than BM25S (1.13) or DeepEval (2.5) for the same capability at this scale.
